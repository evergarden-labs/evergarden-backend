## A. 도메인 모델

### ADR-001 · 코스와 아카이브는 컬럼 하나로 잇는다

`archives.trip_id`를 `NULL 허용 + UNIQUE + ON DELETE SET NULL`로 둡니다.

**이유** — 1:1 관계, 각자 독립 생성, 한쪽을 지워도 상대가 남는 동작이 이 하나로 전부 성립합니다.
연결 테이블을 따로 만들면 같은 동작에 테이블만 하나 늘어납니다.

**영향** — PLAN-05·ARCH-09·ARCH-17 / `archives` 테이블

---

### ADR-002 · `posts`에 "둘 중 하나는 NOT NULL" CHECK 제약을 걸지 않는다

`trip_id`와 `archive_id` 둘 다 `NULL`인 상태를 허용합니다.

**이유** — 직관적으로는 제약을 걸고 싶지만, 사용자가 코스와 아카이브를 **모두 삭제하면**
`ON DELETE SET NULL`이 그 제약을 위반해 **삭제 자체가 실패합니다.**
원본이 없는 게시물은 화면에서 "삭제된 기록입니다"로 처리합니다.

**영향** — COMM-17 / `posts` 테이블

---

### ADR-003 · 게시물의 지역은 등록 시점에 스냅샷으로 굳힌다

`post_regions`에 저장하고, 어디서 온 값인지 `source`로 구분합니다.

**이유** — 코스에서 매번 계산하면 원본이 수정될 때 피드 노출이 조용히 바뀌고,
**원본 코스가 삭제된 게시물은 지역 피드에서 사라집니다.**

**영향** — COMM-02·COMM-04 / `post_regions` 테이블

---

### ADR-004 · 콘텐츠랩 코드를 자체 코드로 바꾸지 않는다

지역과 장소의 기본키에 한국관광 콘텐츠랩의 코드를 그대로 씁니다.

**이유** — 관광지 조회 응답에 담겨 오는 `areacode`·`sigungucode`를 매핑 없이 바로 조인할 수 있습니다.
자체 체계를 만들면 매핑 테이블을 영원히 관리해야 합니다.
대신 외부 API에는 FK를 걸 수 없으므로 마스터 테이블로 적재하고 주기적으로 동기화합니다.

**영향** — `regions`·`places` 테이블 / MAP·GARDEN·COMM-02

---

### ADR-005 · 복제 계보를 두 곳에 남긴다

`trips.origin_trip_id`, `archives.origin_archive_id`

**이유** — 서비스의 차별점이 "코스를 복제하고 재구성하는 것"입니다.
어떤 코스가 몇 번 복제됐는지는 나중에 인기 정렬과 지자체 제공 데이터셋의 근거가 됩니다.

**영향** — PLAN-12·ARCH-15·ARCH-16

---

### ADR-006 · 중복 요청은 애플리케이션이 아니라 DB 제약으로 막는다

좋아요 `(post_id, user_id)` 복합키 · 신고 `(reporter, target)` 유니크 · 정원 해금 `(user_id, garden_object_id)` 유니크

**이유** — 코드로 "이미 있는지 확인 후 저장"하면 동시 요청에서 새어 나갑니다.

**영향** — COMMON-05 / `409` 계열 코드 대부분

---

### ADR-007 · 삭제는 대부분 상태 전환이다

회원 탈퇴, 게시물·댓글 삭제는 행을 지우지 않고 `status`를 바꿉니다.

**이유** — 댓글이 달린 글, 대댓글이 달린 댓글을 물리 삭제하면 **남의 기록까지 사라집니다.**
실제로 지우는 것은 타임캡슐·아카이브처럼 본인 것만 걸린 데이터입니다.

**영향** — AUTH-04·COMM-06·COMM-13·COMM-16

## B. API 규약

### ADR-008 · 응답 봉투를 성공 `{data, meta}` / 실패 `{error}`로 고정한다

**이유** — 두 봉투가 필드를 공유하지 않아 클라이언트가 성공·실패를 한 번에 판별할 수 있습니다.

---

### ADR-009 · `204`를 쓰지 않고 `200`에 `data: null`을 담는다

**이유** — 본문 없는 응답이 섞이면 클라이언트가 상태 코드별로 파싱 분기를 따로 둬야 합니다.
봉투를 항상 같게 유지하는 편이 낫습니다.

---

### ADR-010 · 소셜 로그인은 앱 SDK 토큰 교환 방식으로 한다

앱이 Google·Kakao·Naver SDK로 받은 토큰을 서버에 넘기면 서버가 검증하고 자체 JWT를 발급합니다.
서버가 소셜 로그인 페이지로 리다이렉트하지 않습니다.

**이유** — 모바일 앱이 주 클라이언트입니다. 리다이렉트 방식은 웹 브라우저 전제입니다.

**영향** — AUTH-01·AUTH-02 / `POST /auth/social/{provider}`

---

### ADR-011 · 페이지네이션을 화면 성격에 따라 두 가지로 나눈다

| 방식 | 적용 |
|---|---|
| 커서 (`cursor`, `size`) | 아카이브 목록, 타임캡슐 목록, 커뮤니티 피드 |
| 번호 (`page`, `size`) | 일정 목록, 좋아요 목록, 알림 목록, 관리자 화면 |

기본 `size` 20, 최대 50.

**이유** — 무한 스크롤 화면에서 번호 방식을 쓰면 목록이 갱신될 때 항목이 중복되거나 누락됩니다.
반대로 관리자 화면은 "3페이지로 이동"이 필요합니다.

---

### ADR-012 · 공통 응답은 오퍼레이션마다 반복하지 않는다

`401`(인증 실패) · `403`(차단·탈퇴 회원) · `500`은 전역 규칙으로 두고 각 오퍼레이션에 적지 않습니다.
각 오퍼레이션에는 **거기서만 발생하는** 오류만 적습니다.

**이유** — 60여 개 오퍼레이션에 같은 세 응답을 반복하면 문서가 두 배가 되고,
정작 중요한 도메인 오류가 묻힙니다. **생략한다는 사실 자체는 `info.description`에 명시했습니다.**

---

### ADR-021 · 온보딩 완료와 프로필 수정을 별도 오퍼레이션으로 둔다

`PATCH /users/me/onboarding`(ONB-01)과 `PATCH /users/me`(MY-02)를 나눕니다.
요청 스키마는 같지만 오퍼레이션은 별개입니다.

**이유** — 처음에는 요청 본문이 같다는 이유로 하나로 합쳤으나, **오류 응답이 다릅니다.**
온보딩은 한 번만 가능해 두 번째 호출이 `ONBOARDING_ALREADY_COMPLETED`인 반면
프로필 수정은 몇 번이든 정상입니다. 합쳐 두면 이 차이를 계약으로 표현할 수 없고,
같은 온보딩 동작인데 건너뛰기(`skip`)만 `409`가 나는 비대칭이 생깁니다.
경로 트리에 `/users/me/onboarding/skip`만 있고 부모가 없던 문제도 함께 해소됩니다.

요청 스키마 중복은 `ProfileUpdateRequest` 하나를 `$ref`로 공유해 처리합니다.

**영향** — ONB-01·ONB-02·MY-02 / `ONBOARDING_ALREADY_COMPLETED`

---

### ADR-022 · `posts`에 `share_type` 컬럼을 추가한다

등록 시점에 무엇을 공유했는지(`COURSE` / `ARCHIVE` / `BOTH`)를 별도 컬럼으로 남깁니다.

**이유** — ADR-002에 따라 `trip_id`·`archive_id`는 원본이 삭제되면 `NULL`이 됩니다.
그런데 그러면 **"처음부터 공유하지 않음"과 "공유했는데 원본이 삭제됨"을 구분할 수 없습니다.**
COMM-17이 "삭제된 기록임을 안내받고"를 요구하므로, 구분할 근거가 DB에 있어야 합니다.

`share_type`이 `COURSE`인데 `trip_id`가 `NULL`이면 삭제된 것입니다.
API는 이를 `deletedShare` 배열로 내려보냅니다.

**영향** — COMM-17 / `posts` 테이블에 컬럼 1개 추가 (**ERD 갱신 필요**)

## C. 정책 값

### ADR-013 · 외부 API 장애는 `503`으로 응답한다

**이유** — COMMON-01~07에 분류가 없던 건입니다.
재시도가 무의미한 `500`과 달리 클라이언트가 "잠시 후 다시 시도"로 안내해야 해서 구분했습니다.

**영향** — `TOUR_API_UNAVAILABLE` · `AI_SERVICE_UNAVAILABLE`

---

### ADR-014 · `413` · `415`를 쓰지 않고 `400`으로 흡수한다

**이유** — COMMON-01~07이 정의한 7가지 분류 밖으로 상태 코드를 늘리지 않기로 했습니다.
원인은 `error.code`로 구분합니다.

**영향** — `MEDIA_TOO_LARGE` · `INVALID_MEDIA_FORMAT`

---

### ADR-015 · 파일 상한은 사진 10MB · 영상 200MB(3분) · 1회 20개

허용 형식은 사진 JPEG·PNG·HEIC·WEBP / 영상 MP4·MOV.

**이유** — 통상값입니다. HEIC는 아이폰 기본 포맷이라 빼면 안 됩니다.
**앱이 업로드 전에 리사이즈하는 것을 전제로 한 값입니다** — 원본을 그대로 올리면
1080p 영상 1분이 약 100MB, 4K는 약 350MB라 상한을 금방 넘습니다.

**영향** — MEDIA-01

---

### ADR-016 · 위치 정확도 임계값은 100m

단말이 좌표와 함께 보내는 정확도(iOS `horizontalAccuracy`, Android `getAccuracy()`)를 씁니다.

**이유** — **이 값은 GPS 조작을 막지 못합니다.** 정확도 자체도 단말이 보내는 값이라 함께 조작됩니다.
지하철역처럼 위치가 부정확하게 잡히는 환경을 걸러내는 용도이며,
실질적인 어뷰징 방지는 ADR-018(7일 쿨다운)이 담당합니다.

**영향** — MAP-04 / `LOCATION_ACCURACY_TOO_LOW`
**미반영** — 유저 스토리 카탈로그에는 이 임계값이 적혀 있지 않습니다.

---

### ADR-017 · 공동 편집을 종료해도 참여자의 조회는 허용한다

편집만 막습니다.

**이유** — ① ARCH-13이 "종료 후 복제"인데 내용을 못 보면 복제 대상을 확인할 수 없습니다.
② 동행자와 함께 만든 앨범을 종료했다는 이유로 못 보게 되면 상실감이 큽니다.
③ 완전히 막으면 복제하지 않은 사람은 영영 볼 수 없어 복제를 강요하는 흐름이 됩니다.

**영향** — ARCH-14 (결과 칸에 반영됨) / `COLLABORATION_CLOSED`는 쓰기 요청에만 사용

### ADR-018 · 같은 지역 재인증 쿨다운은 7일

**이유** — 같은 지역 재인증으로 식물이 자라므로(GARDEN-02) 상한이 없으면 무한 성장합니다.
`user_garden_objects.last_grown_at` 기준으로 판정하고,
다음 인증 가능 시각을 `details.availableAt`으로 내려보냅니다.

**영향** — GARDEN-02 (결과 칸에 반영됨) / `REGION_VISIT_COOLDOWN`

### ADR-019 · 인기 피드는 좋아요 순으로 정렬한다

**영향** — COMM-01 (수행 칸에 반영됨) / `posts.like_count` 비정규화 컬럼

### ADR-020 · AI 일정 추천은 "순서 정리"부터 한다

사용자가 가고 싶은 장소를 입력하면 효율적인 동선 순서로 정리합니다.
장소 자체를 추천하는 기능은 포함하지 않습니다.

**이유** — PLAN-09의 상황이 *"가고싶은 곳은 많은데 순서를 어떻게 짜야 할지 모르겠음"* 입니다.
장소는 이미 있고 **순서가 문제**인 상황입니다.
그리고 이 범위는 좌표(`places.lat/lng`)만으로 계산이 가능해
외부 모델 호출 없이 비용 0원, 응답 즉시, 결과 재현 가능하게 만들 수 있습니다.

**영향** — PLAN-09 / 자체 계산으로 구현하면 `AI_SERVICE_UNAVAILABLE`이 필요 없어집니다

### ADR-023 · 미디어는 S3 presigned URL로 앱이 직접 올린다

`POST /media/upload-urls`로 업로드 URL을 발급받아 앱이 S3에 직접 올리고,
`POST /media/complete`로 완료를 알립니다. 파일이 서버를 거치지 않습니다.

**이유** — 영상 상한이 200MB입니다(ADR-015). 이걸 서버가 통째로 받으면
동시 업로드 몇 건만 겹쳐도 메모리와 타임아웃이 무너집니다.
presigned URL은 앱 구현이 2단계로 늘어나는 대신 서버 부하가 0입니다.

형식·용량 검증은 **1단계에서** 합니다. URL을 발급하기 전에 막아야
잘못된 파일이 스토리지에 올라가지 않습니다.

**영향** — MEDIA-01 / `media` 테이블에 `status`(`PENDING`·`READY`) 컬럼 추가 (**ERD 갱신 필요**)
/ `MEDIA_UPLOAD_INCOMPLETE` 코드 신설

### ADR-024 · 공동 편집 초대는 닉네임으로 지목한다

`GET /users/search`로 닉네임을 검색해 `userId`를 얻고, 그 사용자를 초대합니다.
링크·코드 방식은 채택하지 않았습니다.

**이유** — 링크 방식은 초대장 테이블과 오퍼레이션 2개, 만료·재발급 규칙까지 따라옵니다.
지목 방식은 지금 스키마 그대로이고 검색 오퍼레이션 하나만 추가하면 됩니다.

**대가** — 동행자가 **이미 에버가든에 가입해 있어야** 초대할 수 있습니다.
가입 안 한 친구를 부르려면 나중에 링크 방식을 더해야 합니다.

검색은 **정확히 일치하는 닉네임만** 반환합니다. 부분 일치로 훑게 하면
닉네임 목록을 긁어 모으는 통로가 됩니다.

**영향** — ARCH-10 / `GET /users/search` 신설 / 닉네임 중복 허용 여부와 직결됩니다

---

### ADR-025 · 닉네임은 중복을 허용하지 않는다

`users.nickname`에 UNIQUE 제약을 겁니다.

**이유** — ADR-024로 공동 편집 초대를 닉네임 검색으로 하기로 했습니다.
중복을 허용하면 검색 결과에 동명이인이 여럿 나오고, **엉뚱한 사람을 내 여행 앨범에 초대**하게 됩니다.
프로필 이미지로 구분하라고 할 수도 있지만, 이미지를 안 걸어둔 사용자끼리는 방법이 없습니다.

**대가** — 원하는 닉네임을 못 쓰는 경우가 생깁니다.
온보딩을 건너뛴 사용자에게 서버가 자동 생성하는 닉네임도 유일해야 합니다.

**영향** — ONB-01·ONB-02·MY-02·ARCH-10 / `NICKNAME_DUPLICATED` 코드 신설 / `users` 테이블 UNIQUE 제약 (**ERD 갱신 필요**)

### ADR-026 · 위치 조건 타임캡슐은 앱 진입 시 판정한다

앱이 켜질 때 `POST /time-capsules/unlock-check`로 현재 위치를 한 번 보고합니다.
백그라운드 지오펜싱은 쓰지 않습니다.

**이유** — 지오펜싱은 위치 권한을 "항상 허용"으로 받아야 하는데,
사용자가 거부하면 기능이 통째로 죽습니다. iOS는 등록 가능한 지오펜스 개수 제한(20개)도 있습니다.
앱 진입 시 판정은 권한이 "사용 중에만"으로 충분하고 배터리를 쓰지 않습니다.

**대가** — 그 장소에 가더라도 **앱을 열어야 알림이 옵니다.**
타임캡슐이 "언젠가 열리는 것"이라 즉시성이 덜 중요하다고 보고 이 대가를 받아들였습니다.

날짜 조건은 서버 배치가 처리하므로 이 오퍼레이션과 무관합니다.

**영향** — TC-04 / `POST /time-capsules/unlock-check`
