## A. 도메인 모델

### ADR-001 · 코스와 아카이브는 컬럼 하나로 잇는다

`archives.trip_id`를 `NULL 허용 + UNIQUE + ON DELETE SET NULL`로 둡니다.

**이유** — 1:1 관계, 각자 독립 생성, 한쪽을 지워도 상대가 남는 동작이 이 하나로 전부 성립합니다.
연결 테이블을 따로 만들면 같은 동작에 테이블만 하나 늘어납니다.

**영향** — PLAN-05·ARCH-09·ARCH-17 / `archives` 테이블

---

### ADR-002 · `posts`에 "둘 중 하나는 NOT NULL" CHECK 제약을 걸지 않는다

`trip_id`와 `archive_id` 둘 다 `NULL`인 상태를 허용합니다.

**이유** — 직관적으로는 제약을 걸고 싶지만, 사용자가 코스와 아카이브를 **모두 삭제하면**
`ON DELETE SET NULL`이 그 제약을 위반해 **삭제 자체가 실패합니다.**
원본이 없는 게시물은 화면에서 "삭제된 기록입니다"로 처리합니다.

**영향** — COMM-17 / `posts` 테이블

---

### ADR-003 · 게시물의 지역은 등록 시점에 스냅샷으로 굳힌다

`post_regions`에 저장하고, 어디서 온 값인지 `source`로 구분합니다.

**이유** — 코스에서 매번 계산하면 원본이 수정될 때 피드 노출이 조용히 바뀌고,
**원본 코스가 삭제된 게시물은 지역 피드에서 사라집니다.**

**영향** — COMM-02·COMM-04 / `post_regions` 테이블

---

### ADR-004 · 콘텐츠랩 코드를 자체 코드로 바꾸지 않는다

지역과 장소의 기본키에 한국관광 콘텐츠랩의 코드를 그대로 씁니다.

**이유** — 관광지 조회 응답에 담겨 오는 `areacode`·`sigungucode`를 매핑 없이 바로 조인할 수 있습니다.
자체 체계를 만들면 매핑 테이블을 영원히 관리해야 합니다.
대신 외부 API에는 FK를 걸 수 없으므로 마스터 테이블로 적재하고 주기적으로 동기화합니다.

**영향** — `regions`·`places` 테이블 / MAP·GARDEN·COMM-02

---

### ADR-005 · 복제 계보를 두 곳에 남긴다

`trips.origin_trip_id`, `archives.origin_archive_id`

**이유** — 서비스의 차별점이 "코스를 복제하고 재구성하는 것"입니다.
어떤 코스가 몇 번 복제됐는지는 나중에 인기 정렬과 지자체 제공 데이터셋의 근거가 됩니다.

**영향** — PLAN-12·ARCH-15·ARCH-16

---

### ADR-006 · 중복 요청은 애플리케이션이 아니라 DB 제약으로 막는다

좋아요 `(post_id, user_id)` 복합키 · 신고 `(reporter, target)` 유니크 · 정원 해금 `(user_id, garden_object_id)` 유니크

**이유** — 코드로 "이미 있는지 확인 후 저장"하면 동시 요청에서 새어 나갑니다.

**영향** — COMMON-05 / `409` 계열 코드 대부분

---

### ADR-007 · 삭제는 대부분 상태 전환이다

회원 탈퇴, 게시물·댓글 삭제는 행을 지우지 않고 `status`를 바꿉니다.

**이유** — 댓글이 달린 글, 대댓글이 달린 댓글을 물리 삭제하면 **남의 기록까지 사라집니다.**
실제로 지우는 것은 타임캡슐·아카이브처럼 본인 것만 걸린 데이터입니다.

**영향** — AUTH-04·COMM-06·COMM-13·COMM-16

## B. API 규약

### ADR-008 · 응답 봉투를 성공 `{data, meta}` / 실패 `{error}`로 고정한다

**이유** — 두 봉투가 필드를 공유하지 않아 클라이언트가 성공·실패를 한 번에 판별할 수 있습니다.

---

### ADR-009 · `204`를 쓰지 않고 `200`에 `data: null`을 담는다

**이유** — 본문 없는 응답이 섞이면 클라이언트가 상태 코드별로 파싱 분기를 따로 둬야 합니다.
봉투를 항상 같게 유지하는 편이 낫습니다.

---

### ADR-010 · 소셜 로그인은 앱 SDK 토큰 교환 방식으로 한다

앱이 Google·Kakao·Naver SDK로 받은 토큰을 서버에 넘기면 서버가 검증하고 자체 JWT를 발급합니다.
서버가 소셜 로그인 페이지로 리다이렉트하지 않습니다.

**이유** — 모바일 앱이 주 클라이언트입니다. 리다이렉트 방식은 웹 브라우저 전제입니다.

**영향** — AUTH-01·AUTH-02 / `POST /auth/social/{provider}`

---

### ADR-011 · 페이지네이션을 화면 성격에 따라 두 가지로 나눈다

| 방식 | 적용 |
|---|---|
| 커서 (`cursor`, `size`) | 아카이브 목록, 타임캡슐 목록, 커뮤니티 피드 |
| 번호 (`page`, `size`) | 일정 목록, 좋아요 목록, 알림 목록, 관리자 화면 |

기본 `size` 20, 최대 50.

**이유** — 무한 스크롤 화면에서 번호 방식을 쓰면 목록이 갱신될 때 항목이 중복되거나 누락됩니다.
반대로 관리자 화면은 "3페이지로 이동"이 필요합니다.

---

### ADR-012 · 공통 응답은 오퍼레이션마다 반복하지 않는다

`401`(인증 실패) · `403`(차단·탈퇴 회원) · `500`은 전역 규칙으로 두고 각 오퍼레이션에 적지 않습니다.
각 오퍼레이션에는 **거기서만 발생하는** 오류만 적습니다.

**이유** — 60여 개 오퍼레이션에 같은 세 응답을 반복하면 문서가 두 배가 되고,
정작 중요한 도메인 오류가 묻힙니다. **생략한다는 사실 자체는 `info.description`에 명시했습니다.**

---

### ADR-021 · 온보딩 완료와 프로필 수정을 별도 오퍼레이션으로 둔다

`PATCH /users/me/onboarding`(ONB-01)과 `PATCH /users/me`(MY-02)를 나눕니다.
요청 스키마는 같지만 오퍼레이션은 별개입니다.

**이유** — 처음에는 요청 본문이 같다는 이유로 하나로 합쳤으나, **오류 응답이 다릅니다.**
온보딩은 한 번만 가능해 두 번째 호출이 `ONBOARDING_ALREADY_COMPLETED`인 반면
프로필 수정은 몇 번이든 정상입니다. 합쳐 두면 이 차이를 계약으로 표현할 수 없고,
같은 온보딩 동작인데 건너뛰기(`skip`)만 `409`가 나는 비대칭이 생깁니다.
경로 트리에 `/users/me/onboarding/skip`만 있고 부모가 없던 문제도 함께 해소됩니다.

요청 스키마 중복은 `ProfileUpdateRequest` 하나를 `$ref`로 공유해 처리합니다.

**영향** — ONB-01·ONB-02·MY-02 / `ONBOARDING_ALREADY_COMPLETED`

---

### ADR-022 · `posts`에 `share_type` 컬럼을 추가한다

등록 시점에 무엇을 공유했는지(`COURSE` / `ARCHIVE` / `BOTH`)를 별도 컬럼으로 남깁니다.

**이유** — ADR-002에 따라 `trip_id`·`archive_id`는 원본이 삭제되면 `NULL`이 됩니다.
그런데 그러면 **"처음부터 공유하지 않음"과 "공유했는데 원본이 삭제됨"을 구분할 수 없습니다.**
COMM-17이 "삭제된 기록임을 안내받고"를 요구하므로, 구분할 근거가 DB에 있어야 합니다.

`share_type`이 `COURSE`인데 `trip_id`가 `NULL`이면 삭제된 것입니다.
API는 이를 `deletedShare` 배열로 내려보냅니다.

**영향** — COMM-17 / `posts` 테이블에 컬럼 1개 추가 (**ERD 갱신 필요**)

## C. 정책 값

### ADR-013 · 외부 API 장애는 `503`으로 응답한다

**이유** — COMMON-01~07에 분류가 없던 건입니다.
재시도가 무의미한 `500`과 달리 클라이언트가 "잠시 후 다시 시도"로 안내해야 해서 구분했습니다.

**영향** — `TOUR_API_UNAVAILABLE`

---

### ADR-014 · `413` · `415`를 쓰지 않고 `400`으로 흡수한다

**이유** — COMMON-01~07이 정의한 7가지 분류 밖으로 상태 코드를 늘리지 않기로 했습니다.
원인은 `error.code`로 구분합니다.

**영향** — `MEDIA_TOO_LARGE` · `INVALID_MEDIA_FORMAT`

---

### ADR-015 · 파일 상한은 사진 10MB · 영상 200MB(3분) · 1회 20개

허용 형식은 사진 JPEG·PNG·HEIC·WEBP / 영상 MP4·MOV.

**이유** — 통상값입니다. HEIC는 아이폰 기본 포맷이라 빼면 안 됩니다.
**앱이 업로드 전에 리사이즈하는 것을 전제로 한 값입니다** — 원본을 그대로 올리면
1080p 영상 1분이 약 100MB, 4K는 약 350MB라 상한을 금방 넘습니다.

**영향** — MEDIA-01

---

### ADR-016 · 위치 정확도 임계값은 100m

단말이 좌표와 함께 보내는 정확도(iOS `horizontalAccuracy`, Android `getAccuracy()`)를 씁니다.

**이유** — **이 값은 GPS 조작을 막지 못합니다.** 정확도 자체도 단말이 보내는 값이라 함께 조작됩니다.
지하철역처럼 위치가 부정확하게 잡히는 환경을 걸러내는 용도이며,
실질적인 어뷰징 방지는 ADR-018(7일 쿨다운)이 담당합니다.

**영향** — MAP-04 / `LOCATION_ACCURACY_TOO_LOW`
**미반영** — 유저 스토리 카탈로그에는 이 임계값이 적혀 있지 않습니다.

---

### ADR-017 · 공동 편집을 종료해도 참여자의 조회는 허용한다

편집만 막습니다.

**이유** — ① ARCH-15가 "종료 후 복제"인데 내용을 못 보면 복제 대상을 확인할 수 없습니다.
② 동행자와 함께 만든 앨범을 종료했다는 이유로 못 보게 되면 상실감이 큽니다.
③ 완전히 막으면 복제하지 않은 사람은 영영 볼 수 없어 복제를 강요하는 흐름이 됩니다.

**영향** — ARCH-14 (결과 칸에 반영됨) / `COLLABORATION_CLOSED`는 쓰기 요청에만 사용

---

### ADR-018 · 같은 지역 재인증 쿨다운은 7일

**이유** — 같은 지역 재인증으로 식물이 자라므로(GARDEN-02) 상한이 없으면 무한 성장합니다.
`user_garden_objects.last_grown_at` 기준으로 판정하고,
다음 인증 가능 시각을 `details.availableAt`으로 내려보냅니다.

**영향** — GARDEN-02 (결과 칸에 반영됨) / `REGION_VISIT_COOLDOWN`

---

### ADR-019 · 인기 피드는 좋아요 순으로 정렬한다

**영향** — COMM-01 (수행 칸에 반영됨) / `posts.like_count` 비정규화 컬럼

### ADR-020 · AI 일정 추천은 "순서 정리"부터 한다

사용자가 가고 싶은 장소를 입력하면 효율적인 동선 순서로 정리합니다.
장소 자체를 추천하는 기능은 포함하지 않습니다.

**이유** — PLAN-09의 상황이 *"가고싶은 곳은 많은데 순서를 어떻게 짜야 할지 모르겠음"* 입니다.
장소는 이미 있고 **순서가 문제**인 상황입니다.
그리고 이 범위는 좌표(`places.lat/lng`)만으로 계산이 가능해
외부 모델 호출 없이 비용 0원, 응답 즉시, 결과 재현 가능하게 만들 수 있습니다.

**영향** — PLAN-09 / 구현 방식은 ADR-032에서 확정했습니다

### ADR-023 · 미디어는 S3 presigned URL로 앱이 직접 올린다

`POST /media/upload-urls`로 업로드 URL을 발급받아 앱이 S3에 직접 올리고,
`POST /media/complete`로 완료를 알립니다. 파일이 서버를 거치지 않습니다.

**이유** — 영상 상한이 200MB입니다(ADR-015). 이걸 서버가 통째로 받으면
동시 업로드 몇 건만 겹쳐도 메모리와 타임아웃이 무너집니다.
presigned URL은 앱 구현이 2단계로 늘어나는 대신 서버 부하가 0입니다.

형식·용량 검증은 **1단계에서** 합니다. URL을 발급하기 전에 막아야
잘못된 파일이 스토리지에 올라가지 않습니다.

**영향** — MEDIA-01 / `media` 테이블에 `status`(`PENDING`·`READY`) 컬럼 추가 (**ERD 갱신 필요**)
/ `MEDIA_UPLOAD_INCOMPLETE` 코드 신설

### ADR-024 · 공동 편집 초대는 닉네임으로 지목한다

`GET /users/search`로 닉네임을 검색해 `userId`를 얻고, 그 사용자를 초대합니다.
링크·코드 방식은 채택하지 않았습니다.

**이유** — 링크 방식은 초대장 테이블과 오퍼레이션 2개, 만료·재발급 규칙까지 따라옵니다.
지목 방식은 지금 스키마 그대로이고 검색 오퍼레이션 하나만 추가하면 됩니다.

**대가** — 동행자가 **이미 에버가든에 가입해 있어야** 초대할 수 있습니다.
가입 안 한 친구를 부르려면 나중에 링크 방식을 더해야 합니다.

검색은 **정확히 일치하는 닉네임만** 반환합니다. 부분 일치로 훑게 하면
닉네임 목록을 긁어 모으는 통로가 됩니다.

**영향** — ARCH-10 / `GET /users/search` 신설 / 닉네임 중복 허용 여부와 직결됩니다

---

### ADR-025 · 닉네임은 중복을 허용하지 않는다

`users.nickname`에 UNIQUE 제약을 겁니다.

**이유** — ADR-024로 공동 편집 초대를 닉네임 검색으로 하기로 했습니다.
중복을 허용하면 검색 결과에 동명이인이 여럿 나오고, **엉뚱한 사람을 내 여행 앨범에 초대**하게 됩니다.
프로필 이미지로 구분하라고 할 수도 있지만, 이미지를 안 걸어둔 사용자끼리는 방법이 없습니다.

**대가** — 원하는 닉네임을 못 쓰는 경우가 생깁니다.
온보딩을 건너뛴 사용자에게 서버가 자동 생성하는 닉네임도 유일해야 합니다.

**영향** — ONB-01·ONB-02·MY-02·ARCH-10 / `NICKNAME_DUPLICATED` 코드 신설 / `users` 테이블 UNIQUE 제약 (**ERD 갱신 필요**)

### ADR-026 · 위치 조건 타임캡슐은 앱 진입 시 판정한다

앱이 켜질 때 `POST /time-capsules/unlock-check`로 현재 위치를 한 번 보고합니다.
백그라운드 지오펜싱은 쓰지 않습니다.

**이유** — 지오펜싱은 위치 권한을 "항상 허용"으로 받아야 하는데,
사용자가 거부하면 기능이 통째로 죽습니다. iOS는 등록 가능한 지오펜스 개수 제한(20개)도 있습니다.
앱 진입 시 판정은 권한이 "사용 중에만"으로 충분하고 배터리를 쓰지 않습니다.

**대가** — 그 장소에 가더라도 **앱을 열어야 알림이 옵니다.**
타임캡슐이 "언젠가 열리는 것"이라 즉시성이 덜 중요하다고 보고 이 대가를 받아들였습니다.

날짜 조건은 서버 배치가 처리하므로 이 오퍼레이션과 무관합니다.

**영향** — TC-04 / `POST /time-capsules/unlock-check`

### ADR-027 · PostGIS를 쓰지 않는다

좌표는 `numeric(10,7)` 컬럼 두 개(`lat`, `lng`)로 두고, 거리 계산은 애플리케이션에서 합니다.

**이유** — 지금 필요한 공간 연산이 둘뿐입니다.
① 타임캡슐 반경 판정(한 점과 한 점 사이 거리) ② 코스 시각화의 이동 거리 합.
둘 다 하버사인 공식 몇 줄이면 되고, 지역 판정은 이미 콘텐츠랩 API로 하기로 했습니다(ADR-004).

PostGIS를 쓰면 로컬·CI·운영 모든 환경에 확장을 설치해야 하고
JPA에서 쓰려면 `hibernate-spatial`이 붙습니다. 연산 두 개 때문에 치를 비용이 아닙니다.

**언제 다시 볼 것인가** — 방문 인증 어뷰징이 문제가 되어 행정구역 경계로 판정해야 하거나,
"내 주변 관광지"를 콘텐츠랩 없이 직접 검색해야 할 때 다시 검토합니다.

**영향** — MAP-01·TC-04·PLAN-10 / `places`·`regions`·`time_capsules`·`media`의 좌표 컬럼

### ADR-028 · 실시간 공동 편집의 충돌은 마지막 쓰기 우선으로 푼다

항목 단위 잠금을 두지 않습니다. 두 사람이 같은 사진을 동시에 옮기면
나중에 도착한 변경이 이깁니다.

**이유** — 잠금 방식은 잠금 획득·해제뿐 아니라 **앱이 죽었을 때의 타임아웃**까지
서버가 관리해야 합니다. 동행자 2~4명 규모에서 같은 사진을 정확히 같은 순간에
건드릴 확률은 낮고, 그때 잃는 것은 배치 좌표 하나입니다.
그 드문 손실을 막자고 상태 관리를 늘릴 이유가 없습니다.

**변경 단위** — `PATCH /archives/{archiveId}/items/{itemId}`가 보내는 것과 같은 모양,
즉 항목 하나의 `sortOrder`·`layout`·`caption`입니다. 아카이브 전체를 다시 보내지 않습니다.

**아직 남은 것** — 주고받을 메시지 규격과 재접속 시 상태 동기화는 별도 문서가 필요합니다.
OpenAPI는 HTTP만 기술하므로 이 파일에 담을 수 없습니다.

**영향** — ARCH-12 / `GET /archives/{archiveId}/collaboration/session`

### ADR-029 · 아카이브 사진에 캡션을 단다

`archive_items.caption`을 그대로 쓰고, 편집은 `PATCH /archives/{archiveId}/items/{itemId}`에서 합니다.

**이유** — 여행 아카이빙에서 "이때 비 와서 생고생했음" 같은 한 줄이 기록의 절반입니다.

**유저 스토리 보강 필요** — 지금 ARCH-06(콘텐츠 편집)의 수행 작업이
"사진·영상을 추가, 변경, 삭제한다"라 캡션 작성이 드러나지 않습니다.

**영향** — ARCH-06 / `ArchiveItem.caption` 유지

### ADR-030 · 아카이브의 여행 기간은 사진 촬영일에서 계산한다

담긴 사진의 EXIF 촬영 시각 중 가장 이른 날과 늦은 날을 `archives.start_date`·`end_date`에 채웁니다.
**일정을 연결해도 그 기간을 가져오지 않습니다.** 사용자가 입력하지도 않습니다.

**이유** — 일정의 기간은 *계획한* 기간이고, 사진 촬영일은 *실제로 다녀온* 기간입니다.
3박 4일로 계획했다가 하루 일찍 왔으면 앨범의 기간은 3일이어야 합니다.
아카이브는 다녀온 기록이므로 사진 쪽이 맞습니다.

일정 연결(ADR-001)은 화면 사이를 오가는 용도로만 남깁니다.
기간까지 연결에 묶으면 연결을 끊었을 때 기간을 어떻게 할지 같은 규칙이 계속 따라붙습니다.

**한계** — 카카오톡으로 받은 사진이나 스크린샷은 촬영 정보가 지워져 있습니다.
그런 사진만 담긴 아카이브는 기간이 `null`이고 **기간 검색(ARCH-04)에 잡히지 않습니다.**
이름으로는 찾을 수 있습니다.

기간을 손으로 고칠 수 있게 하려면 **유저 스토리를 먼저 고쳐야 합니다** —
ARCH-02의 수행 작업이 "이름, 테마, 대표 색상을 변경한다"라 기간이 없습니다.

**영향** — ARCH-01·ARCH-02·ARCH-04·ARCH-06 / `archives.start_date`·`end_date`는 파생값

### ADR-031 · AI 자동 배치는 제안만 하고 저장하지 않는다

`POST /trips/{tripId}/auto-arrange`는 새 순서를 계산해 돌려주기만 합니다.
적용은 앱이 그 결과를 **기존 `PUT /trips/{tripId}/places/order`에 그대로 보내서** 합니다.

**이유** — 공들여 짠 일정이 버튼 한 번에 뒤집히면 안 됩니다.
되돌리기 스토리가 없으므로, 되돌릴 일이 생기지 않게 만드는 편이 낫습니다.
마음에 들지 않으면 아무것도 하지 않으면 됩니다.

부수 효과가 없으므로 **새 오퍼레이션이 늘지 않습니다.**
응답의 `items`가 순서 변경 요청과 같은 모양이라 앱이 그대로 전달하면 됩니다.

얼마나 나아지는지는 `currentDistanceMeters`와 `proposedDistanceMeters`로 보여줍니다 —
"42km → 28km"처럼 숫자가 보여야 사용자가 적용할지 판단할 수 있습니다.

**영향** — PLAN-09 / `AutoArrangeResult` 신설

### ADR-032 · AI 자동 배치는 좌표 기반 자체 계산으로 만든다

외부 모델을 호출하지 않습니다. 장소들의 위경도로 이동 거리 합이 최소가 되는 순서를 구하고
여행 일수만큼 나눕니다. 장소가 10개 이하면 완전탐색, 그보다 많으면 최근접 이웃 + 2-opt로 충분합니다.

**이유** — PLAN-09가 요구하는 것은 "순서 정리"뿐입니다(ADR-020).
좌표는 이미 `places`에 있어 계산에 필요한 것이 다 있습니다.
자체 계산은 비용이 0이고, 응답이 즉시 나오고, 같은 입력에 항상 같은 결과가 나오며,
외부 장애로 기능이 죽지 않습니다.

**언제 다시 볼 것인가** — "오전엔 실내, 오후엔 야외" 같은 **맥락**을 반영해야 할 때입니다.
그때는 모델과 비용을 따로 검토합니다. API 계약은 그대로라 명세를 고치지 않아도 됩니다.

**영향** — PLAN-09 / `AI_SERVICE_UNAVAILABLE` 코드 폐기

### ADR-033 · 차단에 기간을 두지 않는다

`POST /admin/users/{userId}/blocks`로 차단하면 관리자가 풀 때까지(ADMIN-11) 유지됩니다.
만료 시각도, 자동 해제 배치도 두지 않습니다.

**이유** — 기간제는 `users`에 만료 시각 컬럼과 매일 도는 해제 배치가 따라옵니다.
운영 규모가 작을 때는 관리자가 직접 푸는 편이 확실하고, 해제 이력도 `sanctions`에 남습니다.

**대가** — 위반 정도에 따라 제재 강도를 조절할 수 없습니다.
가벼운 위반에도 "차단 아니면 경고" 둘뿐입니다.
운영하면서 중간 단계가 필요해지면 그때 기간을 도입합니다 —
`USER_BLOCKED`의 `details`에 만료 시각을 더하는 형태라 계약이 크게 바뀌지 않습니다.

**영향** — ADMIN-05·ADMIN-11 / `sanctions` 테이블에 만료 컬럼 없음

### ADR-034 · 마이페이지 기록 현황은 네 갈래 아홉 개로 둔다

기록(아카이브·일정·방문 지역), 정원(해금/전체), 커뮤니티(게시물·받은 좋아요),
타임캡슐(봉인·열 수 있는 것)을 보여줍니다.

**이유** — MY-01이 "내 기록 현황"이라고만 되어 있어 범위를 정해야 했습니다.
서비스의 네 축을 한 화면에서 요약하고 각 화면으로 보내는 관문으로 씁니다.

**주의** — 숫자가 아홉 개입니다. 한 줄로 나열하면 아무것도 눈에 들어오지 않으므로
화면에서는 갈래별로 묶어야 합니다.

`unlockableCapsuleCount`는 특히 값이 있습니다 —
"열 수 있는 타임캡슐 2개"는 사용자를 다시 들어오게 만드는 문구입니다.

정원·타임캡슐 숫자는 전용 화면에도 있어 중복이지만,
마이페이지에서는 **요약과 진입점** 역할이라 중복이 문제되지 않습니다.

**영향** — MY-01 / `MyStats`

### ADR-035 · 관리자 대시보드는 운영 지표와 콘텐츠 지표 일곱 개로 둔다

**운영** 전체 회원 수 · 오늘 가입 · 미처리 신고 · 제재 중 회원
**콘텐츠** 아카이브 수 · 여행 일정 수 · 게시물 수

**이유** — 운영 지표는 관리자가 **지금 무엇을 처리해야 하는지** 알려줍니다.
특히 `pendingReportCount`는 0보다 크면 곧 할 일이라, 화면에서 가장 눈에 띄어야 합니다.
콘텐츠 지표는 행동으로 이어지지는 않지만 서비스가 쓰이는지 보여줍니다.

**넣지 않은 것** — 기간별 추이는 날짜 집계 쿼리가 붙는 데다
데이터가 쌓이기 전에는 빈 그래프만 보입니다.
정원·방문 인증 지표는 서비스 특성을 보여주지만 운영 판단에는 쓰이지 않습니다.
둘 다 필요해지면 그때 더합니다.

**영향** — ADMIN-03 / `AdminDashboard`

### ADR-043 · 이동 거리는 직선 거리로 계산한다

외부 경로 API를 붙이지 않습니다. 자동 배치(ADR-032)도 같은 기준을 씁니다.

**이유** — PLAN-10이 요구하는 것은 "이동 반경이 한눈에 보인다"입니다.
직선 거리로도 어디를 얼마나 돌아다니는지는 충분히 보입니다.
도로 거리를 쓰려면 외부 API가 하나 늘고 호출 한도·비용·장애 처리가 따라옵니다.

두 화면이 같은 기준을 쓰므로 **자동 배치가 "42km → 28km"라고 하면
시각화 화면의 숫자도 28km로 맞습니다.**

**한계** — 실제 도로를 따라간 거리보다 짧게 나옵니다. 화면에 "직선 거리 기준"을 밝히는 편이 낫습니다.

**영향** — PLAN-10·PLAN-09 / `TripRoute.totalDistanceMeters`

### ADR-044 · 인기 피드는 최근 30일 게시물만 줄 세운다

30일이 지난 게시물은 좋아요가 아무리 많아도 인기 피드에 나오지 않습니다.
최신 피드에서는 계속 보입니다.

**이유** — 전체 기간으로 줄을 세우면 초기에 뜬 몇 개가 영원히 상위를 독점합니다.
새로 올린 사람이 상위권에 갈 길이 없으면 공유할 이유가 사라집니다.
여행 정보는 철 지나게 마련이라 30일이 적당합니다 — 7일은 사용자가 적을 때 보여줄 것이 없습니다.

**영향** — COMM-01 / `GET /posts?sort=POPULAR`

### ADR-045 · 게시물 수정은 본문만 허용한다

공유한 코스·아카이브와 지역 스냅샷은 바꿀 수 없습니다.

**이유** — 공유 대상을 바꾸면 사실상 다른 게시물이 되어 **이미 달린 댓글의 맥락이 깨집니다.**
"이 코스 좋네요"라는 댓글 아래에서 코스가 바뀌어 있으면 안 됩니다.
지역 스냅샷(ADR-003)도 다시 계산해야 해서 지역 피드 노출이 조용히 바뀝니다.

잘못 올렸으면 지우고 다시 올리면 됩니다.

**영향** — COMM-05 / `PATCH /posts/{postId}`

### ADR-046 · 신고 사유는 항목에서 고르고 설명을 덧붙인다

`OBSCENE`(음란물) · `ABUSE`(욕설·혐오) · `SPAM`(광고·도배) · `FALSE_INFO`(허위 정보) · `ETC`(기타)
중 하나를 고르고, `detail`에 설명을 덧붙일 수 있습니다. `ETC`이면 설명이 필수입니다.

**이유** — 자유 입력만 받으면 관리자가 한 건씩 읽어야 하고 "별로예요" 같은 무의미한 신고가 섞입니다.
항목이 있으면 유형별로 묶어 처리할 수 있고, 급한 유형(음란물)을 먼저 볼 수 있습니다.

`ETC`에 설명을 강제하는 이유는 "기타"만으로는 관리자가 판정할 근거가 없기 때문입니다.

**영향** — COMM-10·COMM-18·ADMIN-15 / `reports.reason`이 enum, `detail` 컬럼 추가 (**ERD 갱신 필요**)

### ADR-047 · 알림 설정은 종류별 켜기/끄기만 둔다

시간대 같은 다른 축은 두지 않습니다. 경고 알림은 끌 수 없습니다.

**이유** — 지금은 앱 내 알림만 있어 "야간 수신 안 함"이 실질적인 효과가 없습니다.
푸시 알림을 붙일 때 다시 봅니다.

**영향** — NOTI-03 / `notification_settings`

### ADR-048 · 가져온 코스는 새 시작일부터 일차를 다시 매긴다

`POST /posts/{postId}/course/import`에 `startDate`를 받아 원본의 여행 일수만큼 다시 잡습니다.
생략하면 기간 없는 초안으로 들어옵니다.

**이유** — 원본 날짜를 그대로 복사하면 **가져오자마자 지난 여행으로 분류됩니다.**
남의 코스를 가져오는 이유는 앞으로 갈 여행에 쓰려는 것입니다.

**영향** — PLAN-12

### ADR-049 · 장소의 운영 시간·휴무일은 원문 그대로 내려보낸다

콘텐츠랩이 준 문자열을 파싱하지 않고 그대로 전달합니다.

**이유** — 콘텐츠 분류마다 형식이 다릅니다.
"09:00~18:00", "상시개방", "하절기 09:00~19:00 / 동절기 09:00~18:00"이 한 필드에 섞여 있습니다.
요일별 구조로 파싱하면 실패가 잦고, **틀린 영업시간을 보여주는 것이 안 보여주는 것보다 나쁩니다.**

정보가 없는 장소는 `null`이고 앱이 항목을 감춥니다.
기획서의 "이용 시간, 휴무일 활용"을 최소 비용으로 지킵니다.

**영향** — PLAN-07 / `PlaceDetail.useTime`·`restDate`

### ADR-050 · 온보딩을 건너뛴 사용자에게 "여행자+숫자" 닉네임을 준다

`여행자9183` 형태로 서버가 만듭니다. 이미 쓰이는 값이면 다른 숫자로 다시 만듭니다(ADR-025).

**이유** — 커뮤니티에 표시할 이름이 반드시 있어야 합니다.
소셜 계정 이름을 가져오면 본명이 노출될 수 있고, 랜덤 단어 조합은 사전을 관리해야 합니다.
사용자는 마이페이지에서 언제든 바꿀 수 있습니다(MY-02).

**영향** — ONB-02

### ADR-051 · 실시간 편집은 STOMP로, 재접속 시 전체를 다시 받는다

WebSocket 위에 STOMP를 얹고 아카이브 하나가 토픽 하나입니다.
연결이 끊기면 `GET /archives/{archiveId}`로 현재 상태를 통째로 다시 받습니다.
접속한 사람 목록도 주고받습니다.

**STOMP를 쓰는 이유** — `spring-boot-starter-websocket`에 이미 들어 있어
`@MessageMapping`으로 컨트롤러처럼 쓸 수 있습니다. 구독 관리와 방 분리를 직접 짜지 않아도 됩니다.

**전체를 다시 받는 이유** — 변경 이력을 보관하면 얼마나 오래 둘지,
보관 기간을 넘긴 재접속은 어떻게 할지가 새 문제로 따라옵니다.
어차피 그때도 전체를 다시 받아야 합니다. 아카이브 항목이 수십 개 수준이라 통째로 받아도 가볍습니다.

**접속자 목록을 보여주는 이유** — 마지막 쓰기 우선(ADR-028)이라 내 변경이 덮일 수 있습니다.
누가 같이 있는지 보이면 그 상황이 납득되지만, 아무도 안 보이는데 사진이 움직이면
사용자는 앱이 고장 난 줄 압니다.

**중요** — **WebSocket으로는 저장하지 않습니다.** 편집은 전부 기존 HTTP API로 저장하고
WebSocket은 "누가 무엇을 바꿨다"를 알리기만 합니다.
저장 경로가 하나여야 검증·권한·오류 처리를 한 벌만 만듭니다.

**영향** — ARCH-12 / `docs/realtime-editing.md`
